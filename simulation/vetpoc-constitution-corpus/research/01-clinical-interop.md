# 01 — Clinical / Veterinary / Health-Interoperability Test Data

**Lane:** clinical & veterinary interoperability reference data and test corpora for an open-source
compliance test corpus targeting veterinary practice-management (PIMS) and point-of-care (POC)
diagnostic software.

**Date of verification:** 2026-09-05. Every license below was checked by visiting the project page,
license file, or dataset metadata endpoint named in the URL column. Where a license could **not** be
verified, the row says so explicitly rather than guessing.

**Target corpus shape.** Cases are tuples:

```
(case_id, provisions_engaged[], factor_facts{name -> bool}, expected_disposition)
```

So each source below is graded on which of three roles it can play:

| Role | Meaning |
|---|---|
| **FV** — fact vocabulary | Supplies the controlled names/values that boolean factor facts are *about* (e.g. `species_code_is_veterinary`, `drug_is_dea_schedule_ii`, `result_has_loinc_code`). |
| **PF** — payload fixture | Supplies a concrete message/record a case attaches to, so the engine has something real to evaluate. |
| **TO** — test oracle | Supplies an externally-authored ground truth that pins the `expected_disposition` without us inventing it. |

### Veterinary reality check on HL7 v2

There is **no veterinary HL7 v2 profile** in any of the above. Veterinary POC analyzers (IDEXX
VetLab, Abaxis VetScan, Heska) predominantly speak **ASTM E1381/E1394** or vendor-proprietary
protocols rather than HL7 v2; an Abaxis VetScan VS2 ASTM interface specification is publicly mirrored
at https://www.openvpms.org/fileuploads/vs2-astm.txt but the document itself is stamped
*"Abaxis, Incorporated … Confidential Information"* — **do not vendor, do not quote at length.** Read
it only to derive field *names* for factor facts (names and short field labels are facts, not
expression), and cite rather than copy.

### Veterinary DICOM specifics — the important part

**DICOM WG-25 (Veterinary Medicine)** — https://www.dicomstandard.org/activity/wgs/wg-25 — exists and
its charter is to "develop DICOM attributes and workflow-related modifications to support identifying
and describing veterinary patients," covering breed, species, neutered state, owner details,
positioning/body-part descriptions and hanging-protocol nomenclature. **Verified status: "No CPs
under current consideration", current work items "None"** — the group is dormant.

The veterinary attributes are already **in the published standard**, Part 3 §C.7 Patient Module
(verified at https://dicom.nema.org/medical/dicom/current/output/chtml/part03/sect_c.7.html):

| Tag | Attribute | Definition (verified) |
|---|---|---|
| (0010,2201) | Patient Species Description | "The taxonomic rank value (e.g., genus, subgenus, species or subspecies) of the Patient." |
| (0010,2202) | Patient Species Code Sequence | Coded taxonomic rank; **single item only**. |
| (0010,2292) | Patient Breed Description | Free text breed. |
| (0010,2293) | Patient Breed Code Sequence | Coded breed; **multiple items permitted** (mixed breeds). |
| (0010,2294) | Breed Registration Sequence | Registry info for non-human organisms: stock number + registry identification. |
| (0010,2297) | Responsible Person | "Name of person with medical or welfare decision making authority for the Patient." |
| (0010,2299) | Responsible Organization | Organization with the same authority. |

Historical provenance: **CP-643 "Add veterinary identification tags"** (final text 2006-08-22,
https://dicom.nema.org/medical/dicom/Final/cp643_ft.pdf) introduced these; **CP-1478**
(https://dicom.nema.org/medical/dicom/final/cp1478_ft_speciesandstrain.pdf) extended species/strain.
Note the task brief referenced "Supplement 122" — Sup 122 is the *Specimen Identification /
pathology* supplement, **not** the veterinary one. The veterinary work is CP-643 + CP-1478 + WG-25.

**Reuse:** these seven tags are the *canonical fact vocabulary* for veterinary imaging conformance.
Direct factor facts: `has_patient_species_code_sequence`, `breed_code_sequence_has_multiple_items`,
`has_responsible_person`, `species_description_populated_but_code_absent`,
`breed_registration_sequence_present`. Tag numbers and attribute names are **facts and freely
citable**; the standard's explanatory prose is NEMA-copyrighted with **no reuse grant located** — cite,
do not copy. Innolitics' browser (https://dicom.innolitics.com/) is a convenient lookup but is a
third-party rendering, not a license grant.

**Modality worklist in vet practice** — the practical integration surface is the PIMS acting as MWL
SCP and the modality as MWL SCU, with species/breed/owner carried in the worklist response. Vendor
write-up: https://www.asteris.com/blog/modality-worklist-veterinary/ (commercial blog — cite only).
Peer-reviewed conformance study: "DICOM Standard Conformance in Veterinary Medicine",
https://europepmc.org/api/getPdf?pmcid=PMC5788831 — useful for *justifying* which conformance
provisions matter, but check the article's own CC license before quoting.

### Does a veterinary FHIR profile exist?

**Verified answer: no dedicated veterinary FHIR implementation guide exists.** What exists is:

1. `patient-animal` extension (species / breed / genderStatus) — universal extensions pack, CC0.
2. `practitioner-animalSpecies` extension.
3. HL7 Europe Base/Core `Patient-animal-eu` profile —
   https://hl7.eu/fhir/base-r5/0.1.0-ballot/StructureDefinition-Patient-animal-eu.html (ballot).
4. HL7 Europe Laboratory Report `Patient-animal-eu-lab` profile —
   https://hl7.eu/fhir/laboratory/StructureDefinition-Patient-animal-eu-lab.html — **the closest thing
   to a veterinary POC-diagnostics profile that exists**, since it profiles an animal patient
   specifically in a *lab report* context.
5. The US PDMP IG veterinary patient example (above).

Licenses for the HL7 Europe IGs were **not individually verified** on this pass; HL7 IGs are normally
CC0 but confirm before vendoring. The absence of a vet IG is itself a finding: your corpus can
legitimately claim to be first-of-kind, and `no_normative_vet_profile_exists` is a real provision gap
to encode.

## 7. Open questions requiring a second pass

1. **`pydicom-data` license.** No LICENSE at `main` or `master`. Ask upstream or read per-file provenance before any vendoring.
2. **NIST `gvt-core`, `v2-validation`, and CDC `lib-hl7v2-nist-validator` repo-level licenses.** NIST *policy* is public domain and the NIST website says so for the tools; the *repos* did not surface license files on fetch. Confirm before vendoring code.
3. **HAPI HL7v2 license.** Commonly cited as MPL-based; **not confirmed on this pass.**
4. **AAHA License Agreement text.** Determines whether ~5,600 companion-animal diagnostic terms can be vendored. Highest-value open question in this document.
5. **FDA Green Book column schema and a true bulk download.** The catalog entries advertise HTML; the healthdata.gov Socrata resource (`bsk4-rgr7`) should expose CSV/JSON but its metadata page did not render. Also resolve the **ODbL-vs-public-domain** metadata contradiction.
6. **DailyMed / NLM explicit copyright statement.** Public-domain status is near-certain but the statement itself was not captured.
7. **HL7 Europe `Patient-animal-eu` and `Patient-animal-eu-lab` IG licenses.** These are the closest thing to a veterinary lab-report profile; confirm CC0.
8. **VetDataHub actual dataset inventory** and upstream terms of its contributed datasets.
9. **`Work-In-Progress-For-Health/hl7-v2-examples` license.** Would be a convenient v2 fixture set if it turns out to be permissive.
10. **VetXML XSD availability** without consortium membership.
